Filter bar — four directions

Budgeter's all-transactions page is the worst case in the constellation: nine controls of equal weight across two ragged rows. Each option below is a rule set first and a layout second, so whatever wins can be applied to every list page in every app. Shown at budgeter's real content width.

What's there now

Nine controls, all shouting equally. Row two leaves a dead gap. The empty month input renders as --------- ----. Sort is mixed in with the filters even though it changes order, not the set. Nothing tells you whether a filter is even active.

OPTION A

Search + one filter menu

The bar holds search, a Filters button, and sort — nothing else, ever. Every facet lives in the popover. What you've actually set comes back as removable chips, so the bar's height tracks how much filtering you're doing instead of how many filters the page supports.

Rules this sets for every app

  1. A list page's filter bar is exactly: free-text search, one Filters button, one sort control. Nothing else earns a slot.
  2. Every facet lives inside the Filters popover, grouped and labelled. The popover is the only place a facet's full range is shown.
  3. The Filters button carries a count of how many facets are set, and nothing else ever indicates filter state in the chrome.
  4. Applied filters render as removable chips below the bar, and that row does not exist when nothing is set.
  5. Sort is never a filter. It sits last, visually separated, and is labelled with its current value.

Cost: a popover component + an applied-chips component. Biggest build, biggest payoff on dense pages. Scales to any number of facets.

OPTION B

Chips first, search right

Promotes what postings already does. The handful of views you actually use become one-click toggles you can read at a glance; the long-tail facets hide behind "More". Fastest to operate, but only honest when the common filters really are few and well known.

Rules this sets for every app

  1. A facet with five or fewer values you'd actually pick is a row of .filter-chip toggles. Anything larger goes behind More.
  2. The chip row is the page's saved views: the first chip is always the unfiltered default and is active on load.
  3. Free-text search is always right-aligned and always last-but-one; sort is always last.
  4. Chips show state by being active — there is no separate applied-filters row.
  5. A page may have at most one chip row. A second dimension means you needed Option A.

Cost: smallest — .filter-chip already exists and postings ships it. Breaks down on pages with several independent high-cardinality facets (budgeter has three).

OPTION C

Quiet until set

Everything stays on one line and nothing hides, but an unset filter is a dashed ghost and a set one is accent-tinted and states its value. The bar becomes readable left-to-right: you see what's filtering without reading any dropdown's contents.

Rules this sets for every app

  1. Every facet is a pill, never a bare <select>. Unset: dashed border, muted, shows the facet name. Set: solid accent tint, shows the value and a × to clear.
  2. A filter bar is one row. If it wraps on a 1280px viewport, the page has too many facets and the overflow moves behind a menu.
  3. Search is the only full-weight input and always comes first.
  4. No Clear button — clearing is per-pill via ×, because "clear everything" is rarely what you mean.
  5. Sort sits in .toolbar-end, never among the pills.

Cost: one new DS component (the filter pill, with its unset/set states). No popover needed. Still grows horizontally with facet count.

OPTION D

Filters live in the table's own card

A structural fix rather than a control fix: the floating filter panel disappears and the controls join the header of the card they filter, next to the result count. The count and the filters that produced it finally sit together.

Rules this sets for every app

  1. Filters belong to the card they filter. No standalone filter card, ever — it separates the controls from the count they produce.
  2. The card header is: title + "n of total" on the left; search, Filters, sort, primary action on the right, in that order.
  3. The result count always states the filtered figure against the total, so a filter can never be invisible.
  4. Applied filters are removable chips directly under the header, inside the same card.
  5. On a page with no filters, the header keeps the same shape — just fewer controls.

Cost: popover + chips (as A) plus touching each page's card structure. Most consistent result across apps; most markup churn.

Not proposed: token search (category:groceries imported:today parsed from one box). It is the most powerful option and the most work — a parser, a suggestion menu, and a syntax to remember — and it hides the available facets from a user who is scanning. Worth revisiting only if a page ever outgrows Option A's popover.
