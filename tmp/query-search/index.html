Query search — working prototypes

The three demos below are live. Type in them, click the example queries, watch the rows and chips react. Same 14 rows of fake budgeter data in each, same parser underneath — only the syntax and the way you build a query differ.

FIRST

What "filters live in the table's card" meant

Nothing clever — it's about how many boxes are on the page. Today the transactions page is two separate cards: a filter panel floating on top, and a table card below it with its own "Transactions (141)" heading. The controls and the number they produce are in different boxes, so nothing connects "I filtered" to "that's why it says 32".

That's the whole idea: the controls that filter a table go in that table's card header, the count reads "32 of 141" so a filter can never be invisible, and the standalone filter panel disappears. It says nothing about what the controls are — which is what the rest of this page is about. D and a query box are compatible; the query box just becomes the one search control in that header.

OPTION 1

Colon tokens, with autocomplete

The compact form: field:value, no spaces. Bare words search payee and memo. > and < work on amounts and dates. The menu opens as you type a field name, so you never have to remember the vocabulary — type c and it offers category:.

Rules

  1. Grammar is field:value, plus > < >= <= for ordered fields. Terms are ANDed. Quote values with spaces: category:"eating out".
  2. Anything not matching a known field is free text over payee and memo — so a user who never learns the syntax still gets a working search box.
  3. Every term renders as a chip below the input; removing a chip rewrites the query text.
  4. An unknown field is a red chip, never a silent zero-result.
  5. The field vocabulary is declared per page, and the autocomplete is generated from it — never hand-maintained.

Cost: parser + autocomplete + server-side translation per page. Terse to type, least natural to read.

OPTION 2

Spelled-out expressions, Excel-style

What you described: date = today, imported date = today, amount > 50. Spaces allowed around operators, field names can be two words, and is optional. Reads like a sentence; costs more keystrokes and a looser grammar to parse.

Rules

  1. Grammar is field operator value with optional spaces; operators = != > < >= <=. Terms joined by and, or just by spaces.
  2. Field names may contain spaces (imported date) — the page declares its aliases, and they are matched longest-first.
  3. Values are bare words or quoted; today, yesterday, this month, last month and ISO dates are all understood.
  4. Same chip + red-unknown-field rules as option 1.
  5. or is deliberately NOT supported. The moment a query needs or, the honest answer is a saved view, not a longer sentence.

Cost: as option 1 plus a fuzzier tokenizer (spaces are ambiguous: "imported date" is a field, "eating out" is a value). Autocomplete mid-sentence is harder and less precise.

OPTION 3

Builder and query, same thing (recommended)

Both syntaxes above work in this one — but you never have to type either. + Filter walks you through field → operator → value and writes the query for you. You read what it wrote, so you learn the syntax by using the buttons; and once you know it, you just type. The filter popover from option D and the query box stop being two ideas.

Rules

  1. One input per list page. It is the search box and the filter state — there is no second place where filtering lives.
  2. Every control that sets a filter does it by writing into the query. Clicking a category chip in a row, "show me this import", a saved view — all of them append a term you can then see and edit.
  3. The builder accepts either syntax and always writes the terse one, so the canonical form is what you end up reading.
  4. The query is the URL. ?q=imported:today+category:none — so any filtered view is linkable, bookmarkable, and survives a reload.
  5. A query you keep using becomes a saved view: a named chip that expands back into editable terms, never an opaque stored filter.

Cost: highest — parser + autocomplete + builder + saved views. But it is the only one where a user who never learns the syntax and a user who lives in it get the same feature.

BUILD

How this would actually ship

The parser is the shared part and the only genuinely new idea — everything else is wiring. It would live in shared-core.js as a declarative thing: a page hands it a field spec, it hands back a parsed query.

Staging

  1. Parser + chips, client-side only, on budgeter's transactions page. Fields declared in one object; no server change — the existing endpoints already accept the equivalent params, so the parser just maps terms onto them. This is the step that proves the syntax.
  2. Autocomplete menu, generated from the same field spec. This is what makes it usable by someone who hasn't memorised anything.
  3. Builder + URL sync (?q=), which retires the separate filter popover and makes views linkable.
  4. Roll out per page by declaring a field spec: budgeter reports/uncategorized, fitness logbook, mealplanner recipes, postings. A page with two fields declares two; the component is the same.
  5. Saved views last, once real queries exist to save.

Honest caveat: a query language only pays off where there is enough data to sift. Budgeter's transactions and mealplanner's recipes qualify. A page with 9 rows does not — those keep a plain search box, and that is fine. The rule should be "one input per list page", not "a query language everywhere".
